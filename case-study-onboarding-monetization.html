User onboarding and monetization dashboard

SQL analysis in Google BigQuery and a Looker Studio dashboard for WYZR Friends, a live product built by Kainotomia Pte Ltd.

Role
Analysis, SQL and dashboard build
Client type
Internal product team
Tools
Google BigQuery (SQL), Looker Studio
Outcome
Answered part of the business question; limited by the absence of real monetization data

Context

The project manager of WYZR Friends asked for an analysis of user onboarding and monetization. WYZR Friends is a live product built by my company, Kainotomia Pte Ltd, so the work used real user data, with the team’s permission.

My role

I wrote the SQL queries behind the onboarding and monetization dashboard in Google BigQuery and built the dashboard in Looker Studio. I framed the business questions, defined the metrics, made the data-governance decisions described below, and validated the outputs.

Approach

Step 1 Rebuilding the age field

The stored age field was about 40% empty, and its bands overlapped. I recalculated age from date of birth instead. [VERIFY]

Decision

Recalculating from date of birth gives one consistent definition of age, rather than patching a field with gaps and overlapping bands. [VERIFY]

Step 2 Setting a minimum segment size

Segments with fewer than 50 users were excluded. Rates from groups that small were too unstable to compare. [VERIFY]

Trade-off

Some small groups drop out of the view. The rates that remain can be compared with each other. [VERIFY]

Step 3 Modelling revenue as scenarios Simulated

I had no permission to use monetization data, so the revenue component is a simulation Simulated. I built a Looker Studio parameter that switches revenue estimates between conservative, base and optimistic scenarios. [VERIFY]

Decision

Three labelled scenarios show a range and keep the assumption visible. A single simulated number would read as a forecast. [VERIFY]

Data governance and constraints

Working with real product records required setting boundaries on what entered the queries and what could be shown outside the team.

Data-governance summary

Governance rules
Permissions
All permissions were obtained from the WYZR Friends team before the data was used.
Personal data Excluded
Email and phone-number fields were deliberately excluded so personal identifiers never entered the reporting layer.
User volumes Scaled
All user volumes are scaled with multipliers. No real user figures appear anywhere.
Revenue component Simulated
I had no permission to use monetization data, so all revenue estimates are simulated (Simulated) across conservative, base and optimistic scenarios.
Live dashboard access Not linked
The live Looker Studio dashboard is never linked or embedded. It contains production queries and carries risk to the client.

Outcome

The analysis answered part of the business question but produced limited actionable results, largely because real monetization data was not available. The onboarding breakdown rests on real, scaled user data Scaled, while the revenue component shows simulated scenarios Simulated.

What I learned

Most of the work happens before the query is written, and an analysis is only as strong as the data it is allowed to see.

What I would do differently: agree data access, including monetization data, with the project team before fixing the scope of the questions. [VERIFY]

Tools and method

Google BigQuery (SQL) and Looker Studio.

SQL drafted and debugged with AI assistance; business questions, metric definitions, data-governance decisions and output validation are my own.
